# 架构决策记录（ADR）

记录的是**为什么这么做**，而不是怎么配置。配置可以照抄，决策不能。

---

## ADR-001 盒子不做默认网关

**状态**：已采纳

**背景**
有一台闲置的 Linux 机顶盒（百兆 RJ45），直觉上最适合顶替路由器做网关：性能比路由器强，能跑完整 Linux 工具链。实测后发现不对。

**决策**
盒子只做旁路：解析层 + 出口层。**局域网默认网关和唯一 DNS 入口始终是路由器。**

**理由**
- 百兆全双工的理论上限是 100Mbps，扣掉以太网开销后有效吞吐约 94Mbps；
- 单臂旁路意味着同一个包要过两次网口（进 + 出），实际可用带宽再打对折；
- 无线侧回程还要再经过一次桥接，终端体验会明显差于"路由器直接 NAT + HWNAT"。

这不是软件优化能解决的问题，是链路物理上限。**把盒子放在关键路径上，等于用 100Mbps 换一个"看起来更强"的 CPU。**

**后果**
- 内网大流量（NAS、备份、投屏）完全不经过盒子；
- 路由器负责 NAT，HWNAT 仍然有意义；
- 盒子的 CPU 和内存只服务解析与出口，负载长期维持在低位，重启代价也小。

## ADR-002 DNS 分流在边界层终结

**状态**：已采纳

**背景**
两种做法都可以实现"域名命中名单就走特定出口"：
1. 终端直接用盒子的 DNS；
2. 终端用路由器 DNS，路由器把需要分流的查询转给盒子。

**决策**
选 2。终端侧永远只看到 `192.0.2.1`（路由器），盒子隐藏在其后。

**理由**
- 终端配置零改动：换盒子、改上游、升级解析器，都不需要挨个改手机/电视/电脑；
- IPv6 / 双栈、访客网络、IoT 设备这些"配置改不动"的地方，只有边界层统一处理才可控；
- 出了故障只有一个排查入口，回滚也只需要动一台设备；
- 盒子重启期间，路由器还能用缓存兜底，不会全网断解析。

**后果**
- 路由器多一跳转发，但这是内网一跳，成本可忽略；
- 名单与解析策略集中在盒子，路由器只保留必要的 `server=` 与 `ipset=` 片段。

## ADR-003 持久化走 /jffs + bind mount

**状态**：已采纳

**背景**
华硕系固件的根文件系统是 squashfs（只读），`/etc` 下大部分文件在启动时由 `rc` 重新生成。直接改 `/etc/xxx.conf`，当时生效，重启即回滚。

**决策**
- 所有改动落在 `/jffs/`（可写、掉电保留）；
- 用 bind mount 把 `/jffs/...` 覆盖到原路径；
- 挂载动作写在固件支持的启动钩子里，顺序在目标服务启动之前。

**理由**
- 不碰只读分区，不重刷固件，随时可回滚；
- `/jffs` 空间有限（本项目里只剩几 MB），所以只放脚本与配置，不放日志和二进制；
- 备份文件名带时间戳，回滚就是一条 `cp`。

**后果**
- 每次刷固件后需要重新确认挂载点（路径可能变化）；
- `/jffs` 写入寿命有限，避免高频写日志；
- **必须保留一份可回滚的原始资产**——这条在本项目后期被违反过，清理备份时删掉了最后一份出厂文件，后续只能靠重刷固件恢复。见 [pitfalls P-07](pitfalls.md#p-07-清理备份时把出厂原始资产一起删了)。

## ADR-004 dnsmasq 定制只走 conf-dir 片段

**状态**：已采纳

**背景**
`/etc/dnsmasq.conf` 由固件的 `rc` 二进制在启动时重建。直接改主配置（例如加 `user=root`、调 `cache-size`）在重启后会被覆盖，表现为"改了没用"。

**决策**
- 主配置不动；定制项全部写进单独目录里的 `*.conf` 片段；
- 片段目录通过**启动参数或主配置中唯一一处 `conf-dir=`** 注入；
- 片段内**只写可重复项**（`server=` / `ipset=` / `address=` 等）。

**理由**
- 片段独立于主配置的生成逻辑，重启不丢；
- 出问题时删一个文件即可回滚，不需要还原整份主配置；
- 与固件升级解耦。

**后果**
- 片段里出现重复的全局关键字（`user` / `port` / `cache-size` / `no-resolv`）会让 dnsmasq **直接拒绝启动**，全网解析中断。这条踩过一次，代价是约 8 分钟断网。见 [pitfalls P-03](pitfalls.md#p-03-片段重复全局关键字直接把-dnsmasq-搞挂)。
- 因此本仓库提供 `tests/dnsmasq-selftest.sh`，在重启服务之前做重复关键字检测与 `--test` 校验。

## ADR-005 上游解析器必须单实例

**状态**：已采纳

**背景**
上游解析器（本项目用 `pdnsd`）由启动脚本拉起。脚本被重复执行、或服务异常退出后被再次触发时，会出现多个实例抢同一个端口，表现为解析间歇性失败、日志里出现绑定错误。

**决策**
- 启动前先做实例守卫：用 pid 文件 + `ps` 双重确认，已有存活实例则直接退出；
- 守卫只清理**自己启动的**实例，不按进程名盲目 `killall`；
- 停止动作与启动动作都做成幂等。

**理由**
- 端口被占时的表现是"部分查询超时"，很难第一眼定位；
- 盲目 `killall` 会误伤同名的其他组件（这套环境里就有多个名字相近的进程）。

**后果**
- 启动脚本多一次 `ps` 检查，成本可忽略；
- 需要确保 pid 文件路径可写（本项目放 `/jffs`）。

## ADR-006 探活与热更只公开契约

**状态**：已采纳

**背景**
出口层的可用性需要周期性检查，并在状态翻转时告警。

**决策**
仓库只公开**接口与状态机**：
- 输入：使用者本地提供的候选清单文件（`name|host|port`），不进仓库；
- 状态：`UP` / `DEGRADED` / `EMPTY` / `NO_SOURCE`；
- 参数：10 分钟巡检、2 小时冷却、3 分钟宽限、连续 3 次失败判降级；
- 输出：`state.json`（`state` / `healthy` / `total` / `updated_at`）。

**不公开**：候选来源、抓取逻辑、订阅转换、任何具体端点。

**理由**
- 状态机是工程问题，可以讨论；数据来源是另一类问题，不该由仓库承担；
- 接口稳定后，实现可以替换，也不会把使用者绑死在某个来源上。

**后果**
- 使用者需要自己准备候选清单，并在本地生成规则文件；
- 仓库里 `proxies: []`、`proxy-providers: {}` 是刻意的空，不是没写完。
